# CP3.4 — registro nativo por lote (candidato)

El registro no otorga autoridad de ejecución, integración, merge ni despliegue.
CP3.3 y sus archivos de evidencia, incluidas rutas históricas ficticias, quedan
intactos. Este adaptador rechaza las rutas ficticias y exige el árbol real de
cada proyecto: `apps/time-service/`, `apps/web/` o `db/` (también rutas
`backend/`, `frontend/` y `supabase/migrations/` admitidas por el conector).

El perfil `PERFIL-PROG-BACKEND-SPRING-EXP` del selector se traduce de
forma explícita a `PERFIL-PROG-BACKEND-EXP` del runtime fijado;
FRONTEND y DATA conservan su código. Se rechazan perfiles desconocidos,
áreas incompatibles y rutas inexistentes de proyecto. No se modifica ningún
archivo del selector, `vendor/` o `lf_producers_pinned/`.

## Uso seguro

Los registros de CP3.4 requieren un `lots.json` real ya creado por CP3.3,
`state.json` en `LOTS_PLANNED`, un `WorkerTaskSpec` de esquema 1
(con `max_attempts=1` y paths idénticos al lote) y metadatos independientes
de Claude con `holdout_sha256`, `holdout_ref` y `project_ref`.
El cifrado `pilot/holdouts/<t>.oracle.json.age` debe existir realmente.
**El constructor no crea ni lee exámenes ocultos.** Nunca inventar hashes.

El orden de uso es:

1. Partir de `main` limpio, crear rama de preparación para el lote,
   preparar el archivo de tarea y los metadatos de holdout externo.
2. Ejecutar `python3 pilot/orchestrator/native_lot_registration.py
   --request-id <pedido> --lot-id <lote> --task-name <t>
   --template <task.json> --holdout-metadata <holdout-metadata.json>
   --phase register`. La salida **no está fijada** todavía.
3. Revisar y **commitear los tres contextos generados y la tarea nativa**
   en la rama de preparación (nunca en `main`). Ejecutar el mismo comando
   con `--phase seal`: reancla `base_head_sha` al commit que ya contiene
   los contextos. Commitear nuevamente este registro sellado.
4. Ejecutar el comando con `--phase export`: solo ahora se llama a
   `export_task_pack.py`, con el `WorkerTaskSpec` exacto; el paquete
   capturado y su SHA se guardan en `pilot/runs/<pedido>/proposal_requests/`.
   El manifiesto identifica la rama `lf/native-proposal/<t>`, el lote y base.
   La rama de propuesta se publica mediante el flujo gobernado del owner.
5. En lotes dependientes usar `--handoff-proof <recibo.json>` por predecesor;
   cada recibo debe declarar `lot_id`, `merge_sha` y `expected_files`, que
   se comprueban contra el árbol Git del merge en la historia del checkout.
   **Nunca se acepta únicamente un ID de lote como prueba de fusión.** El simulador visible
   prueba DATA → BACKEND sin modelo, sin fingir recepción de un parche real.

Una etapa sin holdout cifrado válido, base Git limpia o contexto incluido en
la base queda BLOQUEADA. La integración del parche verificado corresponde a
CP3.5 y el encadenamiento automático de fusiones a CP3.6.

Estado: adaptador de registro / exportación; el flujo end-to-end real requiere
el proyecto de P5, sus rutas y holdouts independientes. No hay ejecución de IA.
