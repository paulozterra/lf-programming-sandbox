# CP3.5 — integración nativa automática, sin fusión automática

## Disparador gobernado

`.github/workflows/native-verified-integration.yml` escucha exclusivamente
la finalización satisfactoria de **LF Worker native (trusted workflow_run or
manual, no API)**, en `main`, intento 1. Usa solo el código de `main`;
nunca ejecuta ni hace checkout del código del PR de propuesta.

`native_verified_integration.py` consulta por API el run y su job nativo,
confirma origen, PASS, recibo visible y prueba de intento; toma exactamente
`native-verified-patch/worker.patch`. Rechaza artefactos duplicados,
expirados, zip con otros archivos, escapes, entradas symlink, errores y ausencia
de PASS. No utiliza el examen oculto ni el resultado de sus comandos.

Para cada salida, el integrador:
1. Comprueba el registro `native_tasks/<t>.json` de `main`, la base SHA
   ancestro, las rutas permitidas sin globs y ausencia de deriva de esas rutas.
2. Hace `git apply --check --index` y `git apply --index` con **los bytes
   originales** del parche verificado. Rechaza cambios fuera de scope,
   borrados, renombres y rutas de control. Conserva el SHA-256 del parche
   y SHA-256 de cada archivo del índice para revisión de Claude.
3. Abre la rama nueva `lf/native-integration/<t>-run-<id>`, genera el
   próximo CHG libre de `main` y PRs abiertos; `changes.py render` y
   `changes.py check --base origin/main`; abre PR **draft** con el
   CHG automático. No reutiliza ramas de corrida.
4. Incorpora al CHG la URL real del PR, vuelve a verificar y despacha
   `ci.yml` sobre el HEAD final: los pushes con GITHUB_TOKEN no bastan
   para disparar `pull_request` CI.

No fusiona, no aplica `ready-to-merge` ni pretende autenticación de recibos
más allá del PASS real del entorno nativo del sandbox. Claude revisa el
PR independiente; Paulo decide y etiqueta; el Train realiza la fusión.

## CP3.4 en un comando

En una **rama de preparación que no sea main**, con `main` en el
historial y árbol limpio:

```bash
python3 pilot/orchestrator/prepare_native_lot.py \
  --request-id <pedido> --lot-id <lote> --task-name <t> \
  --template /ruta/task.json --holdout-metadata /ruta/metadata.json \
  [--handoff-proof /ruta/recibo-merge.json]
```

El comando ejecuta *register → commit (contexto + registro) → seal
(incluye hash del árbol original) → commit (registro sellado) → export
del paquete mediante worktree de la base exacta*. No hace push ni
crea PR de propuesta; devuelve rama prevista, base y hash de paquete.
Si se interrumpe, la rama conserva los commits; inspeccionarla antes
de reintentar para no crear tareas duplicadas.

## Pruebas visibles y limitaciones

- ZIP malicioso, PASS falso, run ajeno, globs y rutas protegidas bloqueados.
- Aplicación exacta y SHA por archivo; base stale rechazada.
- Orden de las cinco operaciones probado offline.
- No se ejecuta modelo en estas pruebas. Sin exámenes ocultos.
- CP3.6 se reserva el desbloqueo automático por merge de lotes.
