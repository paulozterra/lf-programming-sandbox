# CP3.6 — encadenamiento gobernado de lotes

## Autoridad y disparadores

`.github/workflows/chain-lots.yml` observa la conclusión de
`sandbox-train` y `LF Worker native`. El ejecutor se carga **solo desde
`main`**; comprueba el workflow exacto, repositorio, intento y conclusión.
No interpreta un push del token del Train como prueba de fusión: relee el
commit de dos padres en la línea first-parent, el PR de integración de
`lf/native-integration/<task>-run-<id>`, su `merge_commit_sha`,
`base=main` y las rutas modificadas. No toca los productores fijados ni
ejecuta propuestas no confiables.

La liberación se basa en el DAG de `lots.json`, el SHA registrado en
`state.json` y un manifiesto **revisado previamente por Paulo** en
`pilot/orchestrator/chain_plans/<pedido>.json`. El manifiesto declara,
para cada lote, el ID de tarea nativa, la plantilla de Worker y el archivo
de metadatos del holdout; no contiene ni crea exámenes. Tiene esquema:

```json
{
  "schema_version": "CP36_CHAIN_PLAN_V1",
  "request_id": "mi-pedido",
  "lots_sha256": "<sha256 del lots.json canónico>",
  "production_authority": false,
  "bindings": [
    {
      "lot_id": "SOL-001",
      "task_name": "mi_lote",
      "template_path": "pilot/orchestrator/native_inputs/mi_lote.task.json",
      "holdout_metadata_path": "pilot/orchestrator/native_inputs/mi_lote.holdout.json"
    }
  ]
}
```

El manifiesto debe contener **todos** los lotes, con tareas únicas. Las
plantillas y metadatos deben estar publicados en `main` mediante PR
gobernado, y el ciphertext `pilot/holdouts/<t>.oracle.json.age` debe
existir. El ejemplo anterior es ilustrativo y **no es un plan ejecutable**.

## Merge N → preparación N+1

Al fusionarse una integración verificada de N, `chain_lots.py` forma
recibos Git de todos los predecesores y calcula los sucesores ya listos.
Para cada N+1 que depende del merge actual:

1. Crea worktree aislado desde el **nuevo `main`**, en rama
   `lf/native-registration/<t>-<sha-main>`. No escribe directamente en
   `main`.
2. Actualiza únicamente el campo `base_head_sha` y la huella del
   snapshot a los valores reales del nuevo árbol; conserva las reglas,
   rutas, objetivos y comandos de la plantilla revisada.
3. Ejecuta el **comando real** `prepare_native_lot.py` en ese worktree:
   register → commit → seal → commit → export.
4. Conserva los bytes del paquete oficial y la solicitud de propuesta
   como artefacto `cp36-proposal-request-packs`; no los reconstruye.
5. Añade CHG, `changes.py render/check`, abre PR **draft** para registrar
   el contexto/tarea y despacha el CI para su HEAD. Paulo/Claude/Train
   siguen gobernando la fusión. No crea una propuesta de código ni ejecuta
   modelo de forma automática.

Un mismo task/commit de `main` no se prepara dos veces: una rama de
preparación existente corta el replay. Un predecesor no probado o un
merge ajeno no libera ningún lote.

## Tres fallos y bloqueo

Se consideran exclusivamente runs fallidos de `worker-native.yml`
con prueba oficial `native-attempt-proof` (task, ordinal 1–3,
run ID y pack SHA). Los jobs fallidos antes de producir esa prueba
**no** consumen intento. La detección de tres intentos válidos
1, 2 y 3 sin PASS produce:

- `stage: BLOCKED`;
- `reason_code: CP36_MAX_VERIFIED_ATTEMPTS_EXCEEDED`;
- `blocked_lot_ids` con los lotes afectados;
- `downstream_authorized: false` y `production_authority: false`.

Como el ruleset prohíbe modificar `main` fuera del Train, el
actualizador crea un **PR draft de bloqueo** con el `state.json`
actualizado y CHG. El orquestador considera el pedido bloqueado en
su resultado y no libera sucesores; **la persistencia del estado
BLOCKED en `main` requiere que Paulo etiquete ese PR y el Train lo
fusione**. No se elude esa compuerta para cumplir el objetivo.

## Evidencia

`test_chain_lots.py`: Git real en repositorio efímero, rama de
integración de DATA, merge de dos padres, recibo del commit,
liberación BACKEND, llamada de preparación interceptada (sin modelo),
fallos verificados 1/2/3 y bloqueo; negativos de PR no fusionado,
scope ajeno, ordinal ausente/duplicado o prueba adulterada.

**Alcance:** no se demuestra una corrida del Worker real ni un plan
de P5 activado. La cadena solo opera cuando un owner agrega un
`chain_plan` válido a `main`. La cadena automática no crea exámenes.
