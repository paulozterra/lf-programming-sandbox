Disparador: `workflow_run` terminado del Train, siempre con checkout de
`main`. Se reutiliza el verificador CP3.6 de PR de integración, dos padres,
merges en first-parent y vínculos a lotes del chain_plan. Sin chain_plan
aprobado en `main` no se procesa ningún pedido.

Por cada lote ya fusionado se calcula la huella de análisis A9 y del paquete de
entradas, los archivos realmente modificados y resultados de productores
originales, sin editarlos. Los JSON se guardan como
`pilot/runs/<pedido>/evidence/<lote>-<merge>.json`; el resumen se publica como
`pilot/runs/<pedido>/H_REPORT.md`, mediante PR **draft** y CHG, no mediante
escritura directa a main.

## Contrato de entradas

Cada lote puede tener el archivo explícito y revisado en
`pilot/orchestrator/evidence_inputs/<pedido>/<lote>.json`:

```json
{
  "schema_version": "CP37_EVIDENCE_INPUTS_V1",
  "lot_id": "L1",
  "requirement_links": [
    {"path": "db/migration/V001__example.sql",
     "requirement_ids": ["REQ-EXAMPLE-001"],
     "evidence_ref": "fixture://trace"}
  ],
  "producer_inputs": {}
}
```

**El ejemplo no habilita ejecución ni demuestra trazabilidad.** Las claves
`producer_inputs.PG-XX` corresponden exactamente a los parámetros de cada
productor; no se fabrican precursores, recibos, costes ni huellas. Cuando
falta una entrada, la etapa registra un código `BLOCKED` y no recibe
autoridad. Si falta el archivo completo, H_REPORT lo clasifica
`BLOCKED_CP37_EVIDENCE_INPUTS_MISSING`.

No se lee ningún holdout oculto, no se llama a Testing real, no se modifica
Análisis productivo y no se toca `vendor/` ni los productores fijados.

La política `pilot/test_workflow_yaml_policy.py` ya integrada en el job
obligatorio `estándares (catálogo y checks)` analiza todos los
`.github/workflows/*.yml` con `yaml.safe_load` y requiere `jobs`.
CP3.7 añade además pruebas offline de dos lotes, `REQ-*`, cobertura de
rutas, versiones fijadas y rechazo de autoridad falsa.
