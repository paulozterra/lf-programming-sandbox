## Exclusiones históricas estrictas

La reconstrucción del registro global desde merges acreditados y el aprendizaje EKB de un aviso ya emitido son observación de evidencia anterior, no avance del pedido, nuevo examen, reintento, publicación funcional ni autorización de transición. El watchdog puede conservar candidatos históricos de avisos ya emitidos para el registro catalogado separado y no bloqueante; no se autoriza generar nuevos avisos ni efectos de un pedido suspendido para alimentar EKB. El registro manual global existente mantiene su gobernanza y catálogo; no es un bypass para reactivar pedidos ni para registrar conocimiento no acreditado. Este mantenimiento no escribe en Supabase. La auditoría histórica tiene exclusivamente la guarda R1 anterior; no comparte autorización con EKB ni con el registro global.

## Autorización y drenaje (candidato reforzado)

Además de ready-to-merge, el owner debe publicar una revisión COMMENT (no fingir APPROVE del propio PR) en el HEAD exacto. Texto literal: `LF_LIFECYCLE_AUTHORIZE req-N ACTIVE->SUSPENDING <sha40>`, o la transición siguiente. Para SUSPENDING->SUSPENDED añadir una segunda línea literal: `DRAIN_CONFIRMED: external examiner sessions drained; no legacy replays authorized`. Solo tras verificar efectivamente las sesiones externas. Un cambio de HEAD invalida la autorización y requiere otra revisión; la lectura histórica valida ambos padres del merge. El Train comprueba las corridas no terminales, reservas examiner-working y la política todavía vigente antes de la fusión. Las corridas antiguas o ambiguas deben drenar; no se cancelan automáticamente. El registro histórico global reconstruido desde merges previos sigue siendo observación, no avance de un pedido. No mezclarlo con cambios del pedido.

Límite operativo: GitHub no ofrece atomicidad entre una lectura del control y una escritura remota. Una ejecución heredada que use un checkout anterior al mecanismo no se puede detener desde código nuevo. Debe acreditarse el drenaje y no autorizar replays legacy; el mecanismo aún no está aprobado ni desplegado. La integración inicial se realiza con el Train ya presente en main, no con el código del PR candidato. El archivo inicial debe permanecer vacío. No se interpreta un 404 de política como autorización después del despliegue.

T7 usa el checkout de main vigente y comprueba el control antes de generar, push, PR y dispatch. El SHA del evento se conserva para identificar el delta y debe ser ancestro de main. Los recuperadores nativos revalidan antes de redispatch. La prueba de bootstrap verifica registro inicial vacío y Train anterior sin la nueva guarda cuando el archivo aún no existe en origin/main.

Las guardas incluyen artefactos por tarea de contexto Worker, registros de perdón T32/T37/T38 e insumos de evidencia CP3.7. Los disparadores nativos y el Worker API registrado consultan la autorización antes de admitir ejecución; los avisos de push, feedback y watchdog revalidan justo antes de escribir. Los permisos adicionales de estos workflows son exclusivamente de lectura de issues/PR para verificar autorización, sin ampliar permisos de escritura. Las corridas y el examinador externo previos al despliegue requieren drenaje acreditado; no se ejecutan para validar esta implementación.
